## 阻断

### 1. 关着开关也会退化：iPad 竖式的两可笔迹不再按答案定夺
- 位置：`v2/index.html:1762`（`want = VERT.want(Q.v.vp)`），`v2/vert.js:255`（`want`）
- 现象：`want` 不是多格时返回 `String(p.ans).padStart(p.n, ' ')`。但竖式题型（`IDS`：add3 / sub3 / mul / mul2 / mul3 / div / div2）走的 `parse` 分支返回 `{kind, a, op, b, ans}`，**没有 `n`**。`padStart(undefined)` 不补空格，期望数字整体左移一格。旧代码是 `padStart(n)`，`n` 等于答案格数。
- 复现（node 实测）：`325 + 148 =` 有 4 个答案格。旧 want 是 `[" ","4","7","3"]`，新 want 是 `["4","7","3"]`。按 vertDone 的逻辑模拟：个位写的 3 两可（候选 5、3，排第一的是 5）。旧代码判对、显示 473；新代码判错、显示「你写的是 475」。只要答案格比答案位数多，就会错位：加法、乘法一律如此，减法差比较小时也会。
- 影响：这是线上已有的 iPad 竖式。孩子写对了，因为笔迹两可被判错，进错题。不会把写错的判成对，因为只有改完整串等于答案才采用。
- 建议改法：`want` 加一个参数，`want(p, n)` 在不是多格时用 `padStart(n ?? p.n)`，vertDone 传 `n`（`strokes.length`）。或者 vertDone 里写成 `vp.cells ? VERT.want(vp) : String(inst.ans).padStart(n, ' ').split('')`。再在 `tests/vert.test.js` 加一条：对 `IDS` 和 `BOARD` 每个题型，`want(p, 格数)` 的长度等于 layout 里 `.vcell` 的个数，并且右对齐。这条测试本来就能拦住这次的问题。

## 应修

### 2. iPad 蓝框：组内靠左写时，两可笔迹不按答案定夺
- 位置：`v2/vert.js:255` 的 `want`，`v2/index.html:1772-1774`
- 推理：多格每组格数 = 位数 + 1，现在的题都是 `[1,1]`，所以每组 2 格只写 1 位。孩子很可能写在左边那格，走查 e2e-cells 自己也写在 `nth=0`。`want` 按组内靠右给期望值，左格的期望是空格，两可的数字永远对不上，只能取排第一的候选。`judge` 接受靠左写，但定夺只认靠右写，两边口径不一致。普通填空蓝框原来也有这个问题，多格让它更容易碰到。
- 建议：定夺时按组处理：先找出这组实际写了哪几格，再把这一组答案的数字对齐到写了的那几格。或者在 vertDone 里对每组分别试靠左、靠右两种期望，哪种让 `judge(fixed).ok` 成立就用哪种。

### 3. 手机多位格：孩子写的位数不够时，「你写的是」和错题记录显示错
- 位置：`v2/index.html:1842`（`text = m.vals.join('')`），`v2/index.html:1988`（`typedText` → `cellsLine` → `R.cellsText` 按 `q.cells` 切）
- 复现（node）：`R.cellsText({text:'50 ÷ 4 = □ 余 □', cells:[2,1]}, '52')` 返回 `"52 余 "`。孩子在 2 位格只写了「5」、余数格写「2」，显示和存进错题的 `w` 都是「52 余 」。现在的题都是 `[1,1]`，每格必定正好 1 位（多了会被拦，空的不会提交），所以线上暂时碰不到。但方案说以后多位格不用再改界面，这里会出错。
- 判对不受影响：每格被限制在 `cells[i]` 位以内，拼起来长度等于总位数，就说明每格都写满了，所以整串相等就等于逐格相等。按代码推理确认。
- 建议：`resolve` 的 `typed` 直接用逐格拼好的文字，例如 `m.vals.map((v,k)=>(k?' '+sep+' ':'')+v).join('') + tail`，不要拼成数字串以后再按 cells 切。

### 4. 多格的单元测试默认不跑；`fastMs` 的换格时间没有测试
- `package.json` 的 `npm test` = `node --test tests/`，不带 `MULTI_CELL=1`。`tests/vert.test.js` 的多格蓝框测试和 batch2b2 的「开关打开」测试默认都是 SKIP，CI 和日常 `npm test` 拦不住多格的退化。
- `skills.js:394` 的 `CELL_HOP` 没有单元测试。实测：`fastMs(divrem2 第 1 题, {speed:1000})` 有格时 11400、去掉 cells 是 10400，口答两种都是 8400，行为对，但没有锁住。
- 建议：加一个测试文件，用 `child_process` 以 `MULTI_CELL=1` 再跑一遍 vert 和 batch2b2；或者 `npm test` 改成两遍。补一条：多格 `fastMs` = 不多格 + (格数 − 1) × 1000，口答不加。

## 建议

5. **题库预览在英文日显示「R」**：`v2/index.html:2349` 的 `qpAns` 用了 `cellsLine`，它按 `I18N.on` 把「余」换成 R。但 `#ovQ` 在 i18n 的 SKIP 列表里（`i18n.js:681`），题库预览本来不翻译，于是单日会出现「答案：3 R 1」，其他字都是中文。这条是读代码得出的，没在浏览器里点。改法：题库预览直接用 `R.cellsText`。
6. **错题记录 `w` 跟着当天语言存**：单日存「3 R 2 / 4 and 5/6」，双日存「3 余 2」。蓝框的 `j.text` 和写字板的 `typedText` 都是这样。方案 §4 说 `w` 记「3 余 2」。建议一律存中文（i18n 已有 `^… 余 …$` 的翻译规则，显示时会翻）。
7. **习惯记录「写得清楚」整题一起算**：`index.html:1844` 每格都用 `!Q.x.asked`。只要有一格弹过确认，其他没弹确认的格也记成不清楚。逐格已经有 `r.via`，建议去掉对 `Q.x.asked` 的整题判断，或者只用于弹过确认的那一格。
8. **`m.conf` 只会变成 true**：一格弹过确认后，孩子点这一格重写、这次没弹，这道题仍然不算秒答。这样偏保守，可以接受；如果要精确，就在 `cellCommit` 里按 `m.recs` 重新算。
9. **确认弹窗只显示当前格**：`qcShown`（1826 行）多格时只有一个空位，没有「16 ÷ 5 = 3 余 □」这样的上下文。建议多格时把已填的格和组间字一起显示。
10. **小事**：1711 行的行尾注释「提示回到原位…」跟着 `Q.mc` 那行挪了位置，和代码对不上了。`tests/vert.test.js` 里 `x.padStart(p.groups[k], '')` 什么也不做，可以删。`V.want(p)` 的断言和实现是同一个算法，偏同义反复，建议换成写死的例子（如 `[' ','3',' ','1']`）。iPad 的分数格按方案 §6.2 应该「□/5 画在上方」，现在印在组后面（「/8」），截图看清楚、能用，如果要改，需要和 E 对一下。

## 核对过没问题的
- **跨题残留**：探针跑「多格答错 → 描红 → 继续 → 普通填空题 bond:h:tens」，下一题 `Q.mc = null`，方框上没有 `data-ci`，没有 `cur` 或 `filled`，提示恢复成「在右边写出答案」。点普通题的方框不起作用，phase 还是 `q`。代码上 `showQuestion` 每题都会重新给 `Q.mc` 赋值（1711 行），暂停后重出也走这里。
- **确认弹窗**：用测试栏的「下一题演示识别确认」触发。点「都不是，我重写」后回到同一格（`mc.i` 不变、写字板可写），再触发后选对的候选，填进第 1 格、跳到第 2 格。写完第 2 格判对，因为确认过所以不算秒答（`conf: true`），流程不会卡住。
- **点方框重写**会清掉正在等待的提交计时器（`clearTimeout(Q.submitT)`），只在 `phase === 'q'` 时生效，确认、描红、等待阶段点了没反应。
- **「擦掉」**：第 2 格写了一半点擦掉，第 1 格的值还在，第 2 格重写后正常提交。**「不会」**：第 1 格写好后点不会，判错，描红是「3余1」，讲解正常。
- **描红和「继续」**：多格描红分格印字（中文「余 / 又」，英文「R / and」，e2e 双语都验过）。trace 阶段 `qSchedule` 不会提交，「继续」正常进下一题。
- **答错后 `cellsShow` 不会改到讲解**：答错页 `#qBody` 里没有 `.box`（探针看到空列表），讲解里的答案是 `ans()` 的 span，不会被孩子写的值盖掉。答错页显示的是正确答案「6 余 6」，不是孩子写的「6 余 7」。
- **判对等价于逐格都对**：手机上每格不超过 `cells[i]` 位、空格不会提交，拼起来相等就等于逐格相等。蓝框 `judge` 另外检查每组位数和 `cells[k]` 一致，node 实测「2 / 05」「2 / 两12」「靠左」「空一组」结果都符合预期。
- **`Q.ms`**：每格提交时都会重设为 `qPad.lastUp − t0`，最后提交的那一格（也就是写满时那一格）决定用时。秒答线用的是加过换格时间的 `qLimit`，和 `thinkRatio`、`restMs` 同一套口径。
- **手机多位格能写**（代码推理，没在浏览器里构造 `[2,1]` 的题去写）：`qSchedule` 的 `need = cells[i]`，写不满 2 组会多等 1.5 秒或 4 秒；识别出 2 位不超过上限，按这一格的答案定夺，正常填进去。
- **关着开关时（阻断 1 除外）**：`cellsOf`、`typedText` 都先看 `K.MULTI_CELL`；`fastMs` 只在有 `q.cells` 时加时间，现有题都没有；`ghostInk` 对 `R.ansText` 的结果（只有数字和小数点）切出来的结果和原来一样，小数点仍然画成圆点；`BOARD` 多出来的两个 id 只在 `vertOn(inst)` 里和出题的 id 比对，没有遍历 `BOARD` 去查 `K.ITEM[id].skill` 的地方（grep 过 v2/ 和 tools/），不会报错；测试也只把这两个 id 当成「没登记」。
- **英文一致**：答对整式（「8 R 5」「5 and 4/8」）、你写的是、描红、蓝框组间字、口答（i18n 规则 `^答案是 (.+)$` 会翻成 The answer is 3 R 1）都用 R / and，只有第 5 条的题库预览例外。
